# [Spec] 拾色工坊 MVP：12 个代表性关卡与完整收集闭环

日期：2026-11-16（Asia/Shanghai）。状态：用户已确认采用，作为首个可玩版本的实施与验收规格。

本文综合已接受的 V1 设计、三段参考录屏、用户后续纠正和可点击规则演示。对于本文明确约定的新产品行为，不要求完全复制参考游戏内部实现。此规格定义首个可玩的浏览器验证版本，最终发行目标仍为微信小游戏。

## Problem Statement

用户希望制作一款具有原创瓶型和界面的颜色整理游戏，保留倒水、隐藏层、按目标收取、累计收取揭封、只接水的定色瓶等体验，并随着关卡逐步增加规划难度。

当前已有视觉方向、功能分析和局部规则沙盘，但没有包含完整关卡数据、持久化、可靠动作结算和关卡验收的正式可玩版本。只把原型界面扩展成更多按钮，无法保证隐藏信息、收取链、限制解锁、广告奖励与撤回之间的一致性，也无法保证关卡可解。

用户还明确要求：最多三行、每行最多八瓶；12–18 个总瓶位优先安排为前两行各六个、第三行放余数；每关固定包含两个广告解锁空瓶，用于缺少中转空间时提供帮助。

## Solution

制作“拾色工坊”首个可玩的浏览器验证版本，采用暖白颜料工坊、圆角方瓶、颜色交付卡、封签和固定底座等原创表达。玩家能够开始或继续一关、选择瓶子倒水、显露颜色、形成单色满瓶、按交付目标连续收取、开启受限瓶、获得模拟广告帮助、使用广告获得的打乱/撤回机会或重开，最后完成收集并进入下一关。

交付 12 个可玩、带合法通关回放证据的代表性关卡，分别验证基础倒水、目标更新、隐藏层、封签、定色瓶和组合机制。这 12 个验证关卡不是正式流程最前面的 12 关；前 60 关的逐步教学与难度曲线仍作为后续关卡扩展规划。

广告在本期使用可控制的模拟结果，不连接真实广告服务。每关两个广告空瓶和顶部第四个辅助收集槽分别管理。所有验证关卡须能在不使用任何广告帮助（辅助空瓶、第四槽、打乱或撤回）的情况下完成；广告帮助用于缓解玩家操作造成的局部困境。

首期需要一套可直接运行的游戏验证版本、12 个关卡与回放证据、统一的会话验收入口和少量浏览器端流程验证。现有 HTML 沙盘仅作为行为与视觉参考，不作为正式游戏已经完成的证据。

## User Stories

1. 作为玩家，我希望打开游戏后看到清楚的开始和继续入口，以便立即开始或恢复游玩。
2. 作为玩家，我希望能够选择已提供的代表性验证关卡，以便体验不同机制。
3. 作为玩家，我希望看到当前关卡和已收取数量，以便理解本局进度。
4. 作为玩家，我希望新机制首次出现时有简短的操作说明，以便知道限制是什么。
5. 作为玩家，我希望选中一个瓶子后再选择目标，并能取消选中，以便控制每次倒水。
6. 作为玩家，我希望空瓶或顶层同色且有空间的瓶子可以接水，以便整理颜色。
7. 作为玩家，我希望一次倒水转移顶端连续同色内容并受到目标剩余容量限制，以便操作结果可以预测。
8. 作为玩家，我希望非法动作说明原因且不改变局面，以便不会因误触损失进度。
9. 作为玩家，我希望瓶子不会超出容量或凭空增减颜色，以便规则始终一致。
10. 作为玩家，我希望看到明确的选中状态和合法目标反馈，以便在密集瓶阵中操作。
11. 作为玩家，我希望已知层清晰显示、隐藏层使用遮片或问号，以便判断自己已掌握的信息。
12. 作为玩家，我希望倒走上方内容后按规则显露下一层，以便逐步获得新信息。
13. 作为玩家，我希望同一关重开时颜色和目标不被暗中更换，以便能复盘自己的选择。
14. 作为玩家，我希望有三个默认可用的收集槽，以便理解当前需要交付的颜色。
15. 作为玩家，我希望区分当前收集目标和后续待分配目标，以便提前规划。
16. 作为玩家，我希望单色满瓶在没有匹配目标时留在原处等待，以便不会无条件消失。
17. 作为玩家，我希望满足收取条件的满瓶被收走，并准确增加收取数量，以便获得明确进展。
18. 作为玩家，我希望新目标能够接续收走已准备好的满瓶，以便连续收取过程自然完成。
19. 作为玩家，我希望目标耗尽时槽位明确显示完成，以便知道无需再为该槽准备颜色。
20. 作为玩家，我希望同一瓶不会被两个同色槽重复接收，以便收取数和剩余内容可信。
21. 作为玩家，我希望封签瓶显示所需收取数量和当前进度，以便知道怎样开放它。
22. 作为玩家，我希望只有实际收取满瓶才推进封签门槛，以便不会混淆倒水步数和收取次数。
23. 作为玩家，我希望不同关卡可以有不同封签门槛，以便难度逐步变化。
24. 作为玩家，我希望定色瓶能接收合法内容但不能向外倒水，并明确提示该限制，以便规划单向投入。
25. 作为玩家，我希望装满一只定色瓶只解除该瓶的固定，以便不误以为整行一起开放。
26. 作为玩家，我希望解除固定的满瓶继续遵循交付颜色要求，以便特殊瓶与普通收取规则一致。
27. 作为玩家，我希望每关开局都能看到两个独立的广告空瓶预留位，以便在缺少接水空间时获得帮助。
28. 作为玩家，我希望下方广告空瓶与顶部辅助收集槽有不同名称和状态，以便不会误解奖励内容。
29. 作为玩家，我希望未解锁的广告空瓶不能接水或倒水，以便不会把锁定位误当成可用空瓶。
30. 作为玩家，我希望一次成功广告只解锁我选中的一个空瓶，以便另一个奖励仍可保留。
31. 作为玩家，我希望提前关闭广告时局面和奖励不被错误修改，以便可以稍后再试。
32. 作为玩家，我希望广告失败或无广告可用时有明确反馈，并能返回游戏，以便不会被卡在等待状态。
33. 作为玩家，我希望重复、过期或跨关的广告结果不会重复发奖或解锁错误瓶位，以便对局保持一致。
34. 作为玩家，我希望广告空瓶解锁后能像普通空瓶一样接水、倒水和参与收取，以便它真正提供中转空间。
35. 作为玩家，我希望不使用广告帮助也存在通关路径，以便广告不是预设必付的解题条件。
36. 作为玩家，我希望撤回倒水时保留本关已取得的广告解锁，以便不会再次为同一权益观看广告。
37. 作为玩家，我希望重试当前未完成关卡时保留已经获得的帮助，以便重开不会浪费它。
38. 作为玩家，我希望进入下一关时重新获得两个未解锁的预留位，以便每关规则一致。
39. 作为玩家，我希望能单独模拟解锁第四个收集槽，以便增加可并行接收的目标颜色。
40. 作为玩家，我希望没有待分配目标时不被引导解锁无作用的收集槽，以便奖励的作用明确。
41. 作为玩家，我希望总瓶位包含两个广告预留位且始终不超过三行、每行八个，以便整个工作台可观察。
42. 作为玩家，我希望 12–18 位时前两行各六位、第三行放余数，并让较短行居中，以便排列稳定。
43. 作为玩家，我希望收取和解锁不会让其他瓶子突然挤动位置，以便避免连续操作误触。
44. 作为玩家，我希望在窄屏上也能识别每层颜色和选中目标，以便高密度关卡仍可操作。
45. 作为玩家，我希望颜色同时有符号或编号辅助区分，以便不完全依赖颜色辨识。
46. 作为玩家，我希望使用一次撤回机会恢复上一次倾倒及其引起的收取、目标更新和揭封链，以便完整恢复上一步局面。
47. 作为玩家，我希望重开前有明确确认，并恢复本关最初颜色与目标，以便避免误操作丢失进度。
48. 作为玩家，我希望没有合法动作时得到撤回、重开或解锁剩余空瓶的选择，以便知道如何继续。
49. 作为玩家，我希望提示至少给出一条可执行操作及其原因，不假称任何合法动作都能通关，以便判断提示的可信范围。
50. 作为玩家，我希望能够暂停和返回主页，并继续当前局面，以便中途离开后恢复。
51. 作为玩家，我希望浏览器刷新后仍能恢复已提交的对局、进度和解锁状态，以便不会轻易丢失记录。
52. 作为玩家，我希望不兼容或损坏的存档有清楚的恢复选择，以便不会进入错误或无法操作的局面。
53. 作为玩家，我希望完成本关全部必要收集后通关，即使仍有空瓶或未解锁的广告入口，以便胜利条件清楚。
54. 作为玩家，我希望快速点击或重复回调不会重复结算，以便通关进度只推进一次。
55. 作为玩家，我希望通关后可以进入下一关或返回主页，以便顺畅继续游玩。
56. 作为玩家，我希望完成最后一个验证关卡后看到本版内容已完成，以便不会进入不存在的关卡。
57. 作为玩家，我希望基础声音和震动反馈有开关，并在设备不支持时仍可正常游玩，以便适应不同使用场景。
58. 作为玩家，我希望规则演示广告与真实广告明确区分，且核心游玩不依赖服务器，以便安心验证本地版本。
59. 作为玩家，我希望瓶型、交付卡、限制表现和界面采用原创设计，以便形成独立的游戏体验。
60. 作为关卡维护者，我希望每个验证关卡都有版本、确定输入和可重放的合法通关轨迹，以便修改规则后检查回归。
61. 作为关卡维护者，我希望校验包含收集目标、封签门槛和出水限制，以便不会把普通分色可解误判为整套规则可解。
62. 作为关卡维护者，我希望区分已找到解、已证明无解和搜索预算耗尽，以便不把未知结果当作有效关卡。
63. 作为关卡维护者，我希望隐藏关卡除了有通关轨迹，还经过信息显露与安全选择审核，以便玩家不会被不可知的强制猜测困住。
64. 作为开发与验收人员，我希望通过稳定的游戏会话入口驱动操作并观察结果，以便实现调整后仍可复用行为测试。
65. 作为项目维护者，我希望启动、检查和验收过程有可执行说明，并记录素材与依赖来源，以便后续持续开发。

66. 作为玩家，我希望左下角的打乱按钮重排符合条件的瓶内颜色并保护已满瓶，以便尝试新的操作顺序。
67. 作为玩家，我希望右下角的撤回按钮恢复上一次成功倒水，以便修正最近一次选择。
68. 作为玩家，我希望完整观看对应广告后只获得一次机会、图标右上角显示 1，而不立即执行，以便自己决定何时使用。
69. 作为玩家，我希望成功使用一次道具后角标归零，并在下次需要时重新获取机会，以便清楚知道可用额度。
70. 作为玩家，我希望打乱和撤回分别获得、分别消费，取消或失败不增加次数，以便奖励没有混用。
71. 作为玩家，我希望同一广告结果重复到达时不重复增加次数，有机会时也不要求重看广告，以便次数可信。
72. 作为玩家，我希望没有可打乱对象或可撤回历史时不消耗机会，以便不会浪费已获得的奖励。
73. 作为玩家，我希望撤回或重开不会返还已经消费的道具机会，以便规则一致且不会出现重复使用漏洞。
74. 作为玩家，我希望保存恢复后未使用的机会仍存在且已消费机会不会再出现，以便中途离开不影响权益。
75. 作为玩家，我希望打乱、撤回、广告空瓶和第四收集槽有明确独立的奖励说明，以便知道每次广告换来的具体功能。

## Implementation Decisions

### 范围、运行方式与模块职责

- 本期是移动端布局优先的浏览器可玩验证版本，供桌面浏览器和手机浏览器检查。正式微信运行容器、真实广告、平台授权和商用发布是后续阶段。
- 推荐使用 TypeScript 实现平台无关的规则与会话能力，网页表现层消费公开状态和事件；具体网页渲染库不作为本规格的前置硬约束。正式微信引擎尚未锁定。
- 对外以一个“游戏会话”边界组织开局、玩家动作、广告结果、道具机会获得与消费、打乱、暂停、保存恢复、撤回、重开和关卡切换。规则、目标调度、关卡校验、表现、模拟奖励和本地存储可以有内部职责划分，但不要求把它们分别暴露成大量测试入口。
- 可复用沙盘中已验证的状态关系：满瓶与收取分开、逐瓶解除固定、连续收取后揭封、撤回保留广告权益。原型只提供先例，不能替代正式模块的验证。
- 每个瓶位、收集槽、关卡和广告请求有稳定标识；行列位置属于显示信息，不决定瓶子权限。禁止通过数组临时位置把广告结果发给错误对象。

### 普通倒水、隐藏层与限制

- 容量采用四个离散单位。一次合法倾倒转移源瓶顶部连续同色段，数量取该段长度与目标剩余容量中的较小值。
- 源瓶必须存在、未收走、未遮盖、非广告锁定、非只接水状态，且有内容；本版单色满瓶封口后不再作为倾倒源。
- 目标瓶必须存在、未收走、可接水、未满，且为空或顶部颜色与源色相同。不能向自己倾倒。非法动作不得修改颜色、计数、权益或历史。
- 底层颜色与每层可见信息在开局确定；隐藏层不是空层。动作后使新暴露的顶层可见，保留已知的其他层，不能把所有瓶子强制改为只显示顶层。
- 封签瓶达到本关累计实际收取阈值前不可接水、不可倒出；达到阈值后开放。阈值是关卡配置，支持 2、3、5 等不同值。
- 定色瓶可以接收合法同色内容，不能倒出；本瓶装成单色满瓶时只解除自身固定。初期验证关卡不在同一瓶叠加封签与定色，也不在定色瓶内预填隐藏混色。
- 倾倒、定色解除、目标收取、计数、封签开放与新目标匹配组成一个确定、有限的结算链。表现动画不能重复触发规则结果；结算期间串行处理输入。

### 收集槽与胜利

- 开局三个收集槽免费开放，另有一个独立的辅助收集槽。每个开放槽显示当前颜色目标，单色满瓶匹配后收走；没有匹配目标则原地待收。
- 关卡提供有限且确定的目标库存。用于实现的分配方案是：按固定顺序给开放槽分配当前目标；收取后从尚未分配的目标中补充，新增第四槽也只从未分配目标中取一个，不复制目标或增加颜色需求。
- 预告区展示下一待分配目标；不要把共享待分配目标错误承诺为某个特定槽必定接到的下一单。此项是将原型队列细化为支持第四槽的实现规则，不声称是原作内部算法。
- 多个槽或瓶同时匹配时采用稳定的标识顺序，每瓶最多处理一次。新目标或揭封使其他满瓶可收时，继续检查直到没有可处理事件。
- 最后一批必要内容已经收取、目标库存耗尽且本次结算完成后进入胜利。空瓶、未解锁的广告空瓶和无必要任务的辅助槽不阻塞通关。
- 胜利、进度更新和下一关跳转分别具有一次性保护。最后一个验证关完成后显示本版完成入口，不访问不存在的内容。

### 两个广告空瓶与独立的第四槽

- 每关恰好两个广告空瓶位，开局可见、锁定、内容为空，并计入总瓶位；它们不取代关卡原有的免费空瓶。
- 玩家可以手动选择尚未解锁的某个空瓶。一次完整观看成功只开放该瓶，容量与普通瓶相同，可接水、倒水、装满和被收取；不增加颜色总量或直接增加收取次数。
- 本期实现受控的模拟奖励适配器，明确显示模拟成功、提前关闭、加载失败或无可用广告。每次请求绑定目标、当前关卡、会话代次与唯一请求标识；重复、过期和跨关结果必须被忽略。
- 模拟等待期间停止对局动作；取消或失败不消耗预留位、不回退玩家局面，之后可以重新请求。不得自动发起广告或伪装真实广告。
- 第四个收集槽使用独立奖励目标与权益。解锁它不同时解锁下方空瓶，解锁空瓶也不增加收集槽。没有剩余待分配目标时不提供无实际作用的解锁请求。
- 广告成功取得的权益与可撤回的规则历史分开保存。本关当前游玩记录内的撤回、重开和保存恢复保留权益；重开后的初始辅助空瓶为空，已取得的第四槽重新按初始目标库存分配。
- 开始下一关或新开一个已通关关卡的游玩记录时，使用新的代次和本关默认锁定状态。离开旧记录后到达的旧请求结果不影响新记录。
- 若已解锁的辅助瓶后来装满并收走，该瓶位按普通收取保留空位置，不自动补一个新的空瓶；每关最多取得两个指定空瓶权益。

### 瓶阵排布与输入

- 总瓶位包括普通瓶、免费空瓶、定色瓶、封签瓶及恰好两个广告预留位，最大 24 位；最多三行，每行最多八位，不使用第四行或强制横向滚屏。
- 5–11 位按两行尽量均衡排列；12–18 位前两行各六位，余数在第三行；19–21 位前两行各七位；22–24 位前两行各八位。不存在的第三行不显示，短行居中。
- 典型验收：12 为 6＋6；13 为 6＋6＋1；18 为 6＋6＋6；19 为 7＋7＋5；21 为 7＋7＋7；22 为 8＋8＋6；24 为 8＋8＋8。
- 两个广告空瓶优先固定在最下方至少包含两个位置的一行两端。13 位时广告空瓶放第二行两端，第三行保留一个关卡瓶。所有瓶子的标识与位置在局内保持稳定，收取后不立即压缩重排。
- 390 CSS px 是基础检查尺寸，补充较窄和较宽手机尺寸。八瓶一行不强行承诺每瓶 44 px 的独立横向点击宽度；使用不重叠的整瓶点击区域、选中反馈和目标提示，并检查文字和颜色层是否可辨。
- 触控与鼠标使用同一选源、选目标操作语义。暂停、广告和结算期间不得穿透操作背景瓶子。

### 打乱、撤回的广告机会与满瓶保护

- 左下角固定为打乱，右下角固定为撤回。两个按钮分别维护机会数量，初始均为 0；完整观看成功后只给对应道具 1 次，图标右上角显示 1，不立即执行操作。再次点击、有合法操作并成功提交后扣减为 0，隐藏数字角标并恢复广告提示。
- 首版每种机会暂存上限为 1，有机会时直接使用，不重复请求广告。成功、取消、失败和重复回调的处理独立于下方空瓶和顶部辅助槽，不能跨类型授予奖励。
- 已获机会与已消费记录独立于可撤回棋盘历史保存。未使用机会在保存恢复、重开后保留；首版暂定跨关保留，不能因重放存档或撤回而重复发放或返还已经消费的机会。
- 按本轮明确解释，打乱在每个符合条件的未满瓶内部重排，不跨瓶移动颜色；所有容量已满的瓶子保持原样，包括单色满瓶和混色满瓶。若后续仅保护已完成单色满瓶或改为跨瓶重分配，需明确修改本条，不在实现中自行扩大范围。
- 已收走、未开放封签、锁定广告位、定色瓶、空瓶与无法改变顺序的单色部分瓶不参与打乱。参与瓶子的内容数量、颜色库存、位置和权限不变，目标、收取数与权益也不改变。颜色与对应显露标记一起重排，再按顶层规则显露。
- 正式打乱先构造候选并检查有效变化及关卡可解性，确认后再整体提交和扣次；若无法得到有效候选、校验失败或搜索预算耗尽，则保留原局面和机会并给出原因。沙盘目前只演示次数与保护范围，不作为可解性筛选已完成的证据。
- 没有可撤回倒水或有效打乱对象时，不扣次数，也不要求为无作用操作观看广告。一次成功使用只扣一次；动画、快速点击或重复执行事件不得多扣。
- 打乱本身不是一次倒水。首版暂定成功打乱清空此前倒水历史，从后续倒水重新建立历史；无效打乱不清空。撤回只恢复最近一次成功倒水及其连锁结果，不能免费撤销打乱或返还广告机会。
- 所有道具请求绑定奖励类型、对局代次和请求标识。过期、错误类型和重复完成结果不发奖。未使用机会与账本持久化的实现需同时考虑重复回调及重复恢复。

### 撤回、重开、暂停、提示与存档

- 一次有效撤回先校验机会与历史，再原子恢复上一次玩家倾倒及其导致的全部收取、目标更新、计数、封签显露、定色解除与胜负状态，消费 1 次撤回机会。非法动作不进入历史；广告解锁和道具获得/消费都不是可撤回动作。
- 恢复历史时重新应用本记录已获得的广告权益；不得把已有液体清空、复制颜色或重新锁住成功取得的辅助空瓶。已完成收集的辅助瓶随其规则历史回退，权益不重复授予。
- 重开恢复同关相同版本、种子、颜色、可见信息和目标库存，清空动作历史及计数，并保留本记录已取得的瓶位/槽位权益及未使用道具机会，不返还已消费次数。重开使旧的未完成广告请求失效。
- 暂停和返回主页保存最后一个完整提交的规则状态；恢复时直接显示该状态，不重复执行收取和奖励。正在播放的表现动画不作为唯一真相来源。
- 本地存档至少保留关卡身份与版本、种子、瓶子状态、可见信息、目标库存与当前槽、计数、已获权益、打乱/撤回剩余机会与防重复账本、必要的撤回历史、已完成关卡和设置。保存带版本号，验证结构与一致性后恢复。
- 缺失存档从初始状态开始。损坏或版本不兼容时提示原因并提供重新开始；不得静默产生半恢复局面。存储被禁用或配额不足时，保留当次内存游玩并明确说明无法持久保存。
- 没有合法倒水或可处理收取时，提示撤回、重开及仍可取得的广告空瓶选项；不把任意短暂无动作状态永久判为无法继续。
- 提示在可计算范围内优先给出验证过的解法下一步；只有合法性而无通关保证时明确标为合法操作建议，不宣称必胜。提示不展开全部隐藏颜色；搜索预算耗尽时允许返回暂不能提供可靠提示。
- 提供基础声音和震动开关，持久保存设置。设备不支持音频自动播放或震动时使用视觉反馈并保持可玩，不以平台能力缺失阻断游戏。

### 12 个验证关卡与难度约束

12 个关卡按验收覆盖分组，编号 S01–S12 不等于未来正式关卡 1–12。验证选关界面明确其用途，下一关按验证清单顺序推进。实际前 60 关仍按“基础 → 规划 → 隐藏 → 揭封 → 定色 → 组合”的章节节奏后续制作。

| 验证编号 | 主要目标 | 必须覆盖的行为 |
| --- | --- | --- |
| S01–S03 | 基础倒水，三个关卡 | 选中/取消、同色和空瓶接水、容量不足、连续同色段、非法操作不变、基础胜利 |
| S04–S05 | 目标规划，两个关卡 | 满瓶等待、目标换色、连续收取、目标耗尽、多个匹配的确定顺序 |
| S06–S07 | 隐藏层，两个关卡 | 初始部分可见、新顶层显露、保存恢复保持信息、无需强制猜测的推进路径 |
| S08–S09 | 封签，两个关卡 | 至少两种不同阈值，实际收取才推进、跨揭封撤回及固定初始状态重开 |
| S10–S11 | 定色，两个关卡 | 单只教学、同一行多只分别完成、禁止倒出、解除后等待目标 |
| S12 | 组合，一个关卡 | 隐藏、封签、定色、连续收取组合；两个广告空瓶、第四槽、打乱和撤回机会的独立模拟奖励；包含高密度布局 |

每个关卡均包含两个广告空瓶，且需提供全部广告帮助锁定时的合法通关轨迹。另用最小边界局面覆盖 12、13、18、19、21、22、24 位的排布；这些排布检查数据不能冒充已验证可玩的额外关卡。

关卡须记录固定输入、版本、种子、颜色库存、收集需求、限制与合法回放。示例颜色数和总瓶位需联合构造，至少为教学关保留两个免费自由空瓶，不能把广告位算入这两个。

校验必须考虑：已收走瓶位不再作为免费空瓶、定色瓶不能当作可倒出的中转瓶、封签门槛可在使用该瓶前达到、目标序列与库存一致，以及广告锁定状态下可解。禁止依赖普通分色求解器的结果直接宣布此规则集可解。

找到合法通关轨迹是准入条件；搜索预算耗尽归为未知，不归为可解或不可解。隐藏关另记录安全显露路径和关键分岔审核；全知求解证据不代替玩家信息公平性审核。本期不要求实现无限关卡生成或完整信念状态求解器。

### 视觉、材料与交付

采用暖白工坊、圆角方瓶、颜色交付卡、封签与固定底座。颜色有符号/编号辅助，不使用参考游戏提取的代码、贴图、关卡库、音频或品牌来代替原创实现。

交付可运行应用、12 个关卡及其可回放证据、行为检查、启动与验收说明、已知限制、素材与依赖来源记录。真实微信工程、登录、排行榜、邀请和商业化材料不在本期交付中。

## Testing Decisions

### 已确认的测试边界

**主边界只有一个：游戏会话的公开行为入口。**通过开始/恢复一关、玩家命令、模拟广告结果和保存恢复驱动完整流程，观察公开的可见局面、目标、计数、权益、阶段与拒绝原因。测试不直接调用内部倒水、收集调度、底层数组修改或数据库结构。

关卡轨迹也通过同一个会话入口回放，从开局一直驱动到胜利。合法与非法输入校验通过开始关卡和命令返回结果验证，不为每个内部模块新建一个测试缝隙。

**补充少量浏览器流程检查**：验证鼠标/触控目标、实际行数和居中、隐藏层与固定物表现、左右道具位置、角标 0→1→0、模拟广告弹窗、页面刷新后的继续游戏，以及可点击的通关到下一关。浏览器检查不重复枚举会话规则的全部排列组合。

用户已在采用规格与任务拆分时确认本组验收边界；正式实现按该边界建立行为验证。

### 什么是好测试

- 测试玩家可观察行为和公开契约；允许内部重构后保持原测试成立。
- 使用手工推导的具体局面与预期，以及完整合法通关回放作为独立依据；不把待测算法再计算一遍当作预期。
- 固定关卡输入和随机种子，精确检查一次动作前后、失败后的不变性和持久化后的可见结果。
- 模拟奖励与存储适配器提供明确的成功、取消、失败、损坏、延迟和重复结果；不对内部实现细节做大量桩替换。
- 不把页面截图像素完全一致、函数调用次数或私有字段名称作为主要验收标准。

| T17 | 最后一项必要收取完成 | 胜利仅触发一次，空瓶与锁定广告入口不阻塞 |
| T18 | 进入下一关或验证清单末尾 | 新局使用新身份和两个锁定广告位；最后一关不跳转到不存在内容 |
| T19 | 12 条无广告通关轨迹 | 全部通过公开会话入口重放成功；失败或未知不得纳入交付 |
| T20 | 手机宽度与桌面实际交互 | 最多三行、无横向溢出、瓶层可辨，点击区域不重叠误选 |
| T21 | 对局初始界面 | 打乱在左下、撤回在右下，各为 0 次，显示视频获取提示，无数字 1 |
| T22 | 完整观看打乱或撤回广告 | 只给对应道具 1 次并显示右上角角标，局面和倒水历史不自动执行变化 |
| T23 | 一个道具有 1 次、另一个为 0 次 | 两者独立；使用已有机会不再要求广告，另一道具不增减 |
| T24 | 广告取消、失败、无可用广告 | 两个次数与棋盘均不变，允许返回游戏和重试 |
| T25 | 使用打乱，存在未满混色瓶和满瓶 | 至少一个符合条件瓶的顺序改变；单色满瓶和混色满瓶内容、位置与状态完全不变 |
| T26 | 打乱时有封签、定色、广告锁定、空瓶和已收走瓶位 | 受保护对象不变；参与瓶的单位数和颜色库存守恒，不增加收取数或修改目标 |
| T27 | 一次有效道具操作与快速重复点击 | 成功提交仅扣 1 次，角标消失；零次时不再执行，不多扣或形成负数 |
| T28 | 撤回最近一次倒水及其收取/揭封链 | 完整恢复上一步规则状态，消费 1 次撤回；不恢复已经消费的打乱或撤回机会 |
| T29 | 无撤回历史、无有效打乱对象或候选无法验证 | 不执行、不扣机会；次数为 0 时不引导无效广告，已有的 1 次仍保留 |
| T30 | 重复、过期或错误目标的道具广告回调 | 不增至 2，不恢复已用掉的机会，不解锁空瓶或第四槽 |
| T31 | 重开、保存恢复和跨关恢复机会账本 | 未使用机会按首版保留规则存在；已消费机会不复活，重复恢复不重复发奖 |
| T32 | 成功打乱后尝试撤回、再倒水再撤回 | 不能跨越成功打乱回退旧快照；新的倒水可消耗撤回机会恢复，打乱结果和消费记录保留 |

### 现有先例与覆盖边界

仓库目前没有正式测试套件、生产规则模块或关卡求解器。现有沙盘已通过浏览器人工操作检查禁止倒出、逐瓶解除、连续收取、揭封、胜利、撤回、两个广告空瓶的模拟结果和排布边界；这些是行为先例，不能被写成正式自动化测试已通过。

本规格不承诺已验证真实微信广告 SDK、微信生命周期、真实手机性能、商业化成功率或 60 关的最终难度曲线。实现任务按已确认边界建立类型检查、会话行为验证和关键浏览器检查。

## Out of Scope

- 真实微信广告、支付、登录、好友/省/总排行榜、邀请奖励、社群跳转和运营后台。
- AppID、审核资质、隐私上架材料、广告位配置及正式微信小游戏发布。
- 复制参考游戏代码、素材或精确还原全部原作关卡；REA 解包或反编译不是此规格前置条件。
- 完整 60 关或无限关卡生成、关卡编辑器、多人联机、云存档与跨设备同步。
