# 微信瓶子游戏研究与原创重做规划 v0.3

日期：2026-11-15。状态：研究规划；最新产品和难度设计以 [设计 V1](./design-v1.md) 为准。用户已提供微信入口、三段录屏和核心规则说明；收取与通关循环已明确，发布方式与预算待确认。本文提供完整工作路径，不将建议当作已批准决策，不承诺“换皮即可避免投诉”。

配套文档：[领域词表](../CONTEXT.md)。本机检查记录保存在本地 docs/rea-local-audit.md，不随仓库发布。

## 1. 项目目标与建议路线

已知诉求：使用 REA 研究一个微信游戏；重做瓶子与视觉样式；规划后续开发并降低投诉风险。

建议将项目定义为“参考公开玩法体验，独立实现并形成原创视觉的同类游戏”。REA 用于提取可验证的技术事实；规则文档指导新实现；新的代码、素材、关卡和品牌组成发布版本。

先识别游戏和项目类型，再决定是否需要包分析。若体验观察已足以明确玩法，直接实现通常比完整恢复压缩、混淆和引擎产物更经济。若拥有自己的旧包、授权资料或需要核实复杂状态逻辑，再安排 REA 静态分析。

三段录屏与用户说明已明确：隐藏层与倒水、单色满瓶、按目标颜色收取、槽位后续目标、累计收取达到阈值后揭布，以及完成收集后通关。当前规格见 [核心规则](./daoshuibei-core-rules.md)，REA 适用边界见 [目标评估](./daoshuibei-rea-assessment.md)。打乱与撤回的广告次数已由用户明确，候选打乱与历史边界按最新设计规格处理；尚无源码或可读游戏包。

## 2. REA 在这里的职责与边界

REA 本地版本为 6.5.0，是 CLI/MCP 分析工具层。已验证 JavaScript 应用分析入口、Ghidra 后端就绪和 MCP 自检；详见本机检查记录。

| 输入 | 可采用的路线 | 边界 |
| --- | --- | --- |
| 公开可玩的游戏、截图、录屏 | 人工体验记录 → 状态/交互规格 → 独立实现 | REA 不能从画面直接恢复完整工程；画面足以提供体验事实 |
| 自有或获授权的解包 JS 目录 | REA 静态分析，识别模块、依赖、规则入口 | 需验证能识别微信模块封装；动态代码与混淆可能留下缺口 |
| Cocos 导出内容 | 识别 JS、配置、资源引用，结合运行行为验证 | 不能保证恢复原始场景、Prefab、编辑器关系与作者工程 |
| WASM/原生模块 | 确认格式与架构，按需选择 REA 对应分析后端 | 不因现有 Ghidra 就默认能还原 Unity/Cocos 工程 |
| 微信打包/加密产物 | 先确认格式、来源和必要的独立提取步骤，再把可读内容交给 REA | 未证实 REA 内置微信专用解包/解密流程；不要把通用 extract-artifact 当作 wxapkg 解包器 |
| 服务端功能 | 记录客户端可见协议与行为，设计自己的服务 | 客户端分析无法恢复服务端源代码、数据库或运营配置 |

微信“小程序”和“小游戏”需要先区别：前者通常围绕页面与组件组织，后者通常面向游戏运行环境和 Canvas/WebGL。网页可打开的 H5 游戏也不能直接当作微信小游戏运行时。确认目标的工程类型后再选择适配路线。

## 3. REA 实操步骤

### 3.1 工具准备

现有 CLI 可直接用；本项目无需先补全 Hopper、IDA、JADX。需要让 Codex 直接调用 REA 工具时，再按本机检查文档中的 setup 计划接入。当前已做 dry-run，没有改全局配置。

### 3.2 建立输入与证据目录

在拿到参考资料后按需创建；未确认来源的参考文件不进入发布资产目录。

```text
reference/                  参考录屏、截图及来源记录
research/input/             自有或获授权的可读分析样本
research/evidence/          REA 输出与人工观察记录
spec/                       自主撰写的规则和体验规格
assets/original/             自制或已取得使用权的发布素材
src/                        新实现
```

参考资料和分析输出可能较大，应根据来源与敏感性选择本地保存方式及 Git 忽略规则。为每个样本记录来源、版本、获取日期、文件哈希及分析范围；对源样本做只读留存。

### 3.3 检查可读输入并做有限静态分析

以下是已核对本机 CLI 帮助的命令模板；只有输入目录已存在、内容来源已确认时才执行。本轮没有实际目标数据，未执行这些分析命令。

```powershell
New-Item -ItemType Directory -Path '.\research\evidence' -Force | Out-Null

# 按实际资料位置修改路径。这里假定是已经可读的 JS 目录。
$targetPath = (Resolve-Path -LiteralPath '.\research\input\game-js').Path

rea.cmd inspect-artifact "$targetPath" --format json |
  Set-Content -LiteralPath '.\research\evidence\artifact.json' -Encoding utf8

rea.cmd analyze-javascript-application "$targetPath" `
  --artifact-format directory --format json |
  Set-Content -LiteralPath '.\research\evidence\javascript-analysis.json' -Encoding utf8
```

先看进程退出状态，再检查输出是否为有效结果、是否包含错误/截断/部分分析标记；不能以“生成了 JSON 文件”作为成功标准。若全目录体量太大，依据清单中的真实相对路径使用 `--source-path` 多次指定目标文件。该选项不会自动带入依赖，相关依赖需显式列出。可按需设置 `--analysis-timeout-ms` 和 `--max-heap-mb`，超时或部分结果必须标明未覆盖范围。

重点研究问题：

- 操作输入怎样变为游戏动作，哪些动作会被拒绝？
- 容器状态、容量和内容物如何表达？一次操作搬运多少内容？
- 动画播放和逻辑状态提交的先后顺序是什么？
- 怎样判断胜利、失败、无可用操作？
- 关卡、道具、撤销、重开、存档分别怎样影响状态？
- 哪些是实际规则，哪些只是美术表现或商业化行为？

输出“结论—证据位置—复现步骤—置信度—未解决问题”表。REA 返回的推断须用实际操作验证；缺少 source map 时不能把反编译变量名视为原作者命名。只导入必要的行为结论，素材和代码的可用范围另行记录。

可给分析代理的任务模板：

> 对指定自有或获授权的 JS 目录做静态分析。产出模块职责、操作前置条件、状态变化、胜负判定、关卡数据结构和未知项。每个结论关联具体证据。将事实、推断和缺失分开；遇到未知封装或动态逻辑时明确停止推断。以独立实现所需的行为规格为输出目标。

### 3.4 无可读包时的替代路线

先按正常用户路径体验并录制：首次进入、教程、有效与无效操作、连续点击、暂停、撤销、重开、胜利、失败、切后台恢复。对每个场景记录初始状态、操作、最终状态、反馈时机和不确定点。

如果游戏确为倒水分色，通常能通过这些观察明确主要规则，不必将解包作为项目启动条件。若是瓶子匹配、堆叠、合成等其他玩法，则重新建立对应状态模型。

## 4. 改造范围与投诉风险控制

仅替换颜色、瓶子贴图、名称或图标不足以保证避免投诉。玩法抽象规则与具体代码、美术、音效、文字、关卡编排和整体视觉表达应分别评估；平台审核与司法判断也不等同。

| 维度 | 建议新设计 | 验收证据 |
| --- | --- | --- |
| 瓶子 | 重新设计轮廓、瓶口、底座、材质、高光、选中状态和倾倒姿态 | 设计源文件、草稿、制作记录 |
| 内容物 | 自有配色体系，辅以纹理/符号，重新设计液面和转移反馈 | 调色板、状态图、色觉辨识检查 |
| UI | 独立规划信息层级、容器排列、关卡进度、工具栏和结算 | 新线框图、组件规范、独立文案 |
| 主题与品牌 | 新名称、图标、角色/世界观及宣传素材 | 名称与素材来源检索记录 |
| 动效与音效 | 自制或有许可的点击、倾倒、完成反馈 | 许可台账及源文件 |
| 关卡 | 自己生成和验证难度曲线、教程节奏、特殊机制 | 生成种子、可解性记录、试玩反馈 |
| 代码 | 按行为规格独立实现，管理第三方许可证 | Git 历史、依赖清单、许可说明 |

可供评审的视觉方向示例：“植物调色工坊”——不同造型的实验容器、植物颜料、纸质标签、木质操作台。它只是候选创作方向；需看到参考游戏后确认没有撞上其独特主题与整体构图。

为瓶子建立独立的皮肤定义：外轮廓、填充遮罩、液面锚点、倾倒出口、旋转支点、点击区域、完成效果。逻辑容量使用离散单位；外观适配器将单位映射成可见层。若追求等体积表现，非等宽容器需要面积到液面高度的映射，不能只按均匀高度切层。

建立素材台账：素材名、作者/供应方、来源、许可范围、商业使用/修改权限、凭证位置、发布使用位置。参考游戏提取的贴图、音频、关卡或代码不能因“本地可读”就自动获得发布许可。REA 的开源许可也不会授予被分析内容的使用权。

发布前进行整体对照：轮廓、页面布局、标识、音效、文案、关卡节奏和宣传图是否形成高度相似的整体印象。发现相似处回到设计修改。若商业发布且仍高度贴近某个具体游戏，应让熟悉游戏知识产权的专业人士审查；不存在可靠的“修改百分之多少就安全”阈值。

## 5. 产品与技术方案（待目标确认）

### 5.1 MVP 建议范围

以离线单机体验验证为先：倒水与隐藏层显露、基础教程、12 个代表性切片关卡、撤回、重开、本地进度、音效/震动开关，以及一套完整原创视觉。核心范围包含目标收集槽、满瓶待收与连续收取、按关卡阈值揭布、定色瓶只接不出与逐瓶解除固定、每关两个广告空瓶（首版模拟奖励），以及收取完成后通关；打乱与重开分开；打乱和撤回均需分别观看广告取得一次机会，显示角标 1，成功使用后扣减。关卡数量是建议验收样本，不是最终运营规模。

排行榜、付费、广告、账号、云存档和活动系统留待首个可玩版本后依据发布目标评审；它们会引入后端、权限、隐私与平台配置成本。若参考玩法本身依赖联机，则必须重估该 MVP 范围。

### 5.2 技术选择标准

- 若目标是移动端 2D 微信小游戏且需要持续编辑场景与动画，优先评估 Cocos Creator + TypeScript，并用目标版本的实际微信导出和真机结果决定。
- 若主要是轻量规则验证、很少的场景且团队擅长代码绘制，可评估 Canvas + TypeScript；需要自行处理输入、音频、适配和微信运行环境。
- 若希望先网页验证手感，可做浏览器原型，但需单独安排微信平台适配，不能把浏览器可玩当作微信发布完成。
- 参考游戏的引擎仅是分析事实，新实现不必跟随；最终选择依据人员经验、内容规模与平台约束。

### 5.3 模块职责

| 模块 | 负责 | 关键边界 |
| --- | --- | --- |
| 规则 | 状态、动作合法性、状态迁移、胜负 | 不依赖渲染和微信 API |
| 关卡 | 关卡定义、生成、校验、难度评估 | 区分不可解与求解预算耗尽 |
| 表现 | 瓶子皮肤、布局、动画、输入反馈 | 显示状态不成为规则唯一来源 |
| 进度 | 存档版本、迁移、撤销历史 | 异常退出与旧存档可恢复 |
| 平台 | 微信生命周期、音频、震动、广告等 | 按需实现，便于本地替代 |

若确认是倒水分色，可将容器表示为“从底到顶的颜色序列 + 容量”。倒出动作需明确顶层连续同色块、目标剩余容量、允许接收的颜色以及单次转移单位，不能直接假定采用常见规则。

### 5.4 倒水分色情形的测试与关卡策略

仅在玩法确认后采用：

- 验证每种颜色总量守恒、容量不超限、非法操作不改变状态、撤销准确、胜负判定正确。
- 验证快速点击、同一瓶重复点击、动画期间重开、切后台和恢复时不会重复提交动作。
- 渲染检查细口/宽腹瓶、不同屏幕安全区、内容物顶部/底部裁切和触控区域。
- 求解状态须包含目标收集槽、后续目标与遮盖瓶解锁状态，检查颜色库存与收集需求匹配，排除解锁依赖死锁。
- 使用小规模 BFS 或受限搜索检查示例关卡可解性；搜索超限记为“未知”，不能标记为不可解。
- 从完成态生成关卡时，需要明确设计反向构造规则并重新求解验证。普通合法倾倒往往无法把已完成的单色瓶自动打乱为有趣关卡，不能直接“正向随机倒几步”作为生成算法。
- 难度由解的长度、分支、空容器数量和玩家测试共同衡量，不能只看瓶数或颜色数。

## 6. 分阶段执行与交付

以下工期仅为“一名熟悉相关技术的开发者，常规 2D 离线瓶子谜题，一套原创视觉”的初步工作日估算，不包含排期等待、复杂混淆恢复或平台审核。三段录屏已明确隐藏层、目标队列和收取阈值解锁。原估算仍仅作为常规原型基线，需根据已补齐的机制和最终范围重新估算，不能作为完整参考游戏的固定承诺。

| 阶段 | 工作 | 交付与进入下一阶段的条件 | 初估 |
| --- | --- | --- | --- |
| P0 目标与范围 | 确认游戏、资料来源、平台、预算与成功标准 | 目标卡、资料清单、范围表 | 0.5–1 天 |
| P1 玩法研究 | 体验记录；必要时 REA 静态分析 | 带证据的规则规格、未知项；关键规则可以复现 | 1–3 天 |
| P2 原型 | 独立规则内核，几个代表性关卡与占位画面 | 核心操作闭环、规则验证通过 | 2–4 天 |
| P3 原创视觉 | 方向评审、瓶子系统、界面、音效、动效 | 一套原创视觉与来源记录；移动端操作清晰 | 3–5 天 |
| P4 MVP 集成 | 关卡、存档、撤销、教程、微信适配 | 12 个代表性切片关卡可玩，生命周期和真机验证完成 | 3–5 天 |
| P5 发布准备 | 性能、兼容性、相似性复核、平台材料 | 验收清单与候选发布包 | 2–4 天 |

合计约 12–22 个工作日。商业化、后端、复杂解包和额外皮肤单独估算。微信主体、类目资质、隐私声明、提审材料及适用审批要求应在确定发行方式后查当时的官方规定，不以此估算代替平台审查。

建议性能目标：以约定真机名单验证稳定帧率和触控响应，项目期望 60 fps，低端设备可接受门槛另定；记录首屏加载、内存和包体数据。包体与接口限制以选定发布工具和当期微信文档为准，不在未知版本下写死数字。

## 7. 验收清单

- 核心规则均有来源证据和新实现验证；推测与已确认内容分开。
- MVP 流程闭环，示例关卡有可解性证据，撤销与重开正确。
- 瓶子、UI、文案、音效、品牌及关卡都有原创或许可记录。
- 已检查整套表达与参考游戏的相似性；没有“改颜色就安全”的假设。
- 真机通过不同长宽比、前后台切换、低帧率、连续触摸、存档恢复测试。
- 微信 API 调用异常有合理反馈；涉及广告时，取消、失败与奖励发放幂等另行验收。
- 发布版本不携带无必要的参考材料、分析证据或无发布权限的资源。
- 最终可编辑工程、构建步骤、测试记录、素材台账和已知限制齐备。

## 8. 决策树与采访记录

已完成的事实调查：REA 安装、版本、CLI/MCP/Ghidra 状态、Codex 接入缺口；尚未应用 setup。

目前没有形成难以逆转的技术决策，因此暂不创建 ADR。后续引擎/平台或协作边界出现真实权衡并被确认后再记录 ADR。

```text
目标与资料
├─ 游戏身份 + 可观察入口/已有资料
│  ├─ 确认工程类型与玩法
│  └─ 判断是否需要 REA，以及可处理的输入
├─ 用途与发行范围
│  ├─ 本地练习 / 内部验证 / 微信商业发行
│  └─ 平台、账号、资质及商业化需求
├─ 保留的体验 + 原创差异目标
│  ├─ 瓶子、美术、UI、音效、关卡
│  └─ 是否增加玩法差异
└─ 人员经验 + 时间预算
   ├─ 技术路线与 MVP 范围
   └─ 排期、验收设备与发布门槛
```
